## Общее описание решения

В этой работе я сделал плагин для CLion. Сначала он только вставлял шаблоны C++: функцию `main`, цикл `for` и класс. Затем я добавил команду проверки имён и форматирования кода по правилам, которые используются в лабораторных работах.

Команды находятся в меню **Tools**. Также их можно вызвать двухэтапными горячими клавишами. Вставку шаблонов и применение исправлений можно отменить через **Ctrl+Z**.

Плагин написан на Java в IntelliJ IDEA. Для сборки используется JDK 21 и Gradle Wrapper. Работу проверял в CLion 2026.2.2 на Windows 11 25H2.

## Структура проекта

Основные файлы:

- `src/main/java/ru/student/cpptemplates/InsertMainAction.java` — вставка функции `main`.
- `src/main/java/ru/student/cpptemplates/InsertForAction.java` — вставка цикла `for` с учётом отступа строки.
- `src/main/java/ru/student/cpptemplates/InsertClassAction.java` — вставка заготовки класса.
- `src/main/java/ru/student/cpptemplates/CheckLabNamingAction.java` — запуск проверки имён, чтение предложенных замен, показ результата и применение изменений.
- `src/main/java/ru/student/cpptemplates/LabCodeFormatter.java` — запуск Clang-Format.
- `src/main/resources/lab-clang-tidy.yaml` — настройки проверки имён.
- `src/main/resources/META-INF/plugin.xml` — описание плагина, зависимости, команды и горячие клавиши.
- `build.gradle.kts` — зависимости проекта и выбор целевой версии CLion.
- `settings.gradle.kts` — версии инструментов сборки и репозитории зависимостей.
- `gradle.properties` — группа, версия проекта и настройки Gradle.
- `gradlew`, `gradlew.bat`, `gradle/wrapper/` — файлы Gradle Wrapper.

## Команды плагина

### Insert C++ Main

Команда находится в классе `InsertMainAction`. Она вставляет заготовку программы:

```cpp
#include <iostream>

int main() {
    
    return 0;
}
```

После вставки курсор находится на пустой строке внутри `main`, после четырёх пробелов. Можно сразу писать код.

Для использования нужно открыть пустой файл и выбрать **Tools → Insert C++ Main**.

### Insert C++ For Loop

Команда находится в классе `InsertForAction`. Она вставляет цикл со счётчиком от 0 до 9:

```cpp
for (int i = 0; i < 10; ++i) {
    
}
```

Плагин берёт отступ строки перед курсором и использует его для цикла. Для тела добавляются ещё четыре пробела. Курсор устанавливается внутрь тела цикла.

Например, если сначала вставить `main`, а затем сразу вызвать **Tools → Insert C++ For Loop**, получится:

```cpp
int main() {
    for (int i = 0; i < 10; ++i) {
        
    }
    return 0;
}
```

Для правильных отступов команду нужно вызывать на пустой строке после отступа.

### Insert C++ Class

Команда находится в классе `InsertClassAction`. Она вставляет класс с конструктором, двумя методами и закрытым полем:

```cpp
class MyClass {
public:
    MyClass() = default;

    void setValue(int value) {
        value_ = value;
    }

    int getValue() const {
        return value_;
    }

private:
    int value_ = 0;
};
```

Курсор ставится перед именем `MyClass`. Если переименовывать класс вручную, нужно также изменить имя конструктора.

Для проверки я вставлял класс после `#include`, перед функцией `main`. Команда вызывается через **Tools → Insert C++ Class**.

### Check Lab Naming

Эта команда проверяет имена в открытом C++-файле и подготавливает форматирование. Для анализа используется Clang-Tidy, а для отступов, пробелов и переносов — Clang-Format, которые входят в установленный CLion.

Правила имён хранятся в `lab-clang-tidy.yaml`. За основу взяты требования из лабораторных работ. Дополнительно добавлено правило для локальных `const`-переменных.

Основные правила:

| Что проверяется | Правило | Пример имени |
|---|---|---|
| Пространства имён | `lower_case` | `my_namespace` |
| Классы и структуры | `CamelCase` | `MyClass` |
| Шаблонные параметры | `CamelCase` | `ValueType` |
| Функции | `CamelCase` | `CalculateSum` |
| Обычные переменные | `lower_case` | `item_count` |
| Поля | В профиле заданы `lower_case` и суффикс `_` для соответствующих категорий полей | `item_count_` |
| Элементы перечислений | `CamelCase` с префиксом `k` | `kReady` |
| Настроенные категории констант | `CamelCase` с префиксом `k` | `kMaxCount` |

Для констант заданы правила для `constexpr`, глобальных, статических, локальных констант и констант-полей. Проверка различает категории символов; точные настройки перечислены в YAML-файле.

В настройках Clang-Tidy префикс `k` задаётся отдельно от `CamelCase`. Для констант-полей используются параметры `ConstantMemberCase` и `ConstantMemberPrefix`.

Форматирование основано на Google Style, но отступ и отступ продолжения строки установлены в четыре пробела. Табуляция отключена. Метки `public:` и `private:` выравниваются относительно начала класса, короткие функции остаются многострочными.

Это проверка имён и форматирование, а не автоматическая проверка всех требований к качеству кода. Команда не оценивает смысл названий или правильность алгоритма.

#### Как использовать

1. Подготовить C++-проект по инструкции ниже.
2. Открыть файл `.cpp`, `.cc` или `.cxx`.
3. Выбрать **Tools → Check Lab Naming**.
4. Посмотреть сообщения и предлагаемый итоговый код.
5. Нажать **«Применить исправления»**, если изменения подходят, либо **«Закрыть»**.

Например, до обработки:

```cpp
int main(){
int itemCount=3;
const int maxCount=10;
if(itemCount<maxCount){
itemCount++;
}
return itemCount;
}
```

После применения:

```cpp
int main() {
    int item_count = 3;
    const int kMaxCount = 10;
    if (item_count < kMaxCount) {
        item_count++;
    }
    return item_count;
}
```

Переименования применяются и к объявлениям, и к найденным использованиям в этом файле. Если имена уже правильные, команда всё равно проверяет форматирование.

Переименование и форматирование применяются вместе и отменяются одним нажатием **Ctrl+Z**. После применения результат можно сохранить через **Ctrl+S**.

## Горячие клавиши

| Команда | Первое нажатие | Второе нажатие |
|---|---|---|
| Insert C++ Main | Ctrl+Alt+Shift+T | M |
| Insert C++ For Loop | Ctrl+Alt+Shift+T | F |
| Insert C++ Class | Ctrl+Alt+Shift+T | C |
| Check Lab Naming | Ctrl+Alt+Shift+T | N |

Сначала нужно нажать первое сочетание, отпустить все клавиши и нажать вторую букву без Ctrl, Alt и Shift. Проверял сочетания в английской раскладке.

Они зарегистрированы в `plugin.xml` для keymap `$default`. При конфликте сочетания можно изменить в **Settings → Keymap**.

## Как плагин подключается к IDE

CLion основан на IntelliJ Platform. В плагине я использую систему действий этой платформы. Классы команд наследуются от `AnAction`, а в `plugin.xml` связываются с пунктами меню `Tools` и сочетаниями клавиш. Там же объявлены зависимости `com.intellij.modules.platform` и `com.intellij.clion`.

При вызове команды IDE передаёт `AnActionEvent`. Из него можно получить текущий проект, редактор или открытый файл. Для изменения текста используется `Document`, а `WriteCommandAction` оформляет изменение как действие, которое можно отменить.

Команды шаблонов просто вставляют подготовленный текст. Команда проверки работает иначе: она сохраняет текущий документ и запускает Clang-Tidy в фоновой задаче, чтобы не блокировать интерфейс.

Clang-Tidy получает настройки из ресурса плагина и параметры компиляции из `compile_commands.json`. Найденные исправления экспортируются через `--export-fixes`. Плагин читает этот YAML с помощью SnakeYAML Engine, собирает изменённый текст и передаёт его Clang-Format. Затем показывает результат пользователю. До нажатия кнопки предлагаемые исправления в документ не применяются.

Перед применением проверяется, что документ и файл на диске не изменились после начала анализа. Для замен учитываются байтовые позиции в UTF-8.

## Основные методы

### actionPerformed(AnActionEvent event)

Параметр `event` содержит контекст вызова команды. Метод ничего не возвращает (`void`).

В командах шаблонов он получает редактор, вставляет текст и перемещает курсор. В `CheckLabNamingAction` он подготавливает файл, запускает фоновую задачу анализа и форматирования, а затем открывает окно результата.

### update(AnActionEvent event)

Управляет доступностью команды. В командах шаблонов проверяются проект, редактор и возможность записи в документ. Для `Check Lab Naming` также проверяются локальное расположение файла и расширение `.cpp`, `.cc` или `.cxx`.

Возвращаемого значения нет (`void`).

### getActionUpdateThread()

Возвращает `ActionUpdateThread.BGT`. Это задаёт фоновый поток обновления доступности действия.

### prepareFixes(...)

Метод класса `CheckLabNamingAction`. Читает экспортированные исправления, проверяет их и возвращает подготовленный текст. Если замен нет, возвращает `null`. Пересекающиеся замены и изменения других файлов не применяются.

### applyChanges(...)

Проверяет актуальность результата и заменяет текст документа через `WriteCommandAction`. Поэтому все изменения можно отменить вместе.

### LabCodeFormatter.format(...)

Получает текст, путь исходного файла и индикатор выполнения. Запускает Clang-Format и возвращает отформатированный текст. Для обмена с процессом используются временные файлы.

## Подготовка C++-проекта для проверки стиля

Этот раздел относится к проекту на C++, открытому в CLion, а не к Java-проекту плагина.

Команда использует базу компиляции `compile_commands.json`. Для её генерации нужно добавить в `CMakeLists.txt` перед созданием цели:

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

Затем выполнить **Reload CMake Project**. Используемый генератор CMake должен поддерживать экспорт базы компиляции, например Ninja или Makefiles.

В текущей реализации ожидается файл:

```text
<корень C++-проекта>/cmake-build-debug/compile_commands.json
```

Для моего тестового проекта файл `CMakeLists.txt` выглядит так:

```cmake
cmake_minimum_required(VERSION 4.3)
project(plug)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
set(CMAKE_CXX_SCAN_FOR_MODULES OFF)

add_executable(plug main.cpp)
```

Сканирование модулей отключил, потому что в базе компиляции появились параметры GCC, которые не понимал Clang-Tidy. Мой тестовый проект не использует модули C++. Для проектов с модулями такую настройку нельзя переносить без проверки.

## Сборка и запуск плагина

Нужно открыть проект плагина в IntelliJ IDEA, выбрать JDK 21 для Gradle и дождаться синхронизации.

Кроме зависимостей IntelliJ Platform, в `build.gradle.kts` добавлена библиотека для чтения YAML:

```kotlin
implementation("org.snakeyaml:snakeyaml-engine:2.9")
```

Команды выполняются в терминале из корня проекта плагина:

```powershell
.\gradlew.bat compileJava
.\gradlew.bat runIde
.\gradlew.bat buildPlugin
```

- `compileJava` — компиляция Java-кода.
- `runIde` — запуск отдельного CLion с разрабатываемым плагином.
- `buildPlugin` — сборка установочного ZIP в `build/distributions`.

Команда `runIde` остаётся работающей, пока открыто тестовое окно CLion. Перед новым запуском нужно закрыть предыдущий экземпляр.

## Установка

1. Выполнить `buildPlugin`.
2. В обычном CLion открыть **Settings → Plugins → ⚙ → Install Plugin from Disk…**.
3. Выбрать ZIP из `build/distributions`. Распаковывать его не нужно.
4. Перезапустить CLion, если он попросит.
5. Проверить команды в меню **Tools**.

После изменения исходников для обновления установленного плагина нужно заново собрать и установить ZIP.

## Ограничения

### Команды шаблонов

- Вставляют код в позицию курсора и не заменяют выделенный текст.
- Не проверяют расширение файла.
- Не проверяют наличие другой функции `main`, такого же класса или строки `#include`.
- Для правильного отступа `for` нужно вызывать на пустой строке после отступа.
- Имена `setValue` и `getValue` в шаблоне класса пока сохранены в исходном виде. Проверка стиля может предложить их переименовать согласно профилю.

### Проверка и форматирование

- Текущая версия рассчитана на Windows и проверена с CLion 2026.2.2. Пути к встроенным инструментам определяются относительно каталога CLion.
- Поддерживаются локальные файлы UTF-8 с расширениями `.cpp`, `.cc`, `.cxx`.
- База компиляции должна находиться в `cmake-build-debug` относительно корня открытого проекта.
- Обрабатывается один открытый файл. Если экспортированные замены затрагивают другие файлы, применение блокируется.
- Команда не гарантирует корректность переименования символов во всём многофайловом проекте. Например, использования в отдельно компилируемом файле могут не попасть в анализ текущего файла.
- Если документ или файл на диске изменился после анализа, нужно запустить проверку ещё раз.
- При ошибке анализа, чтения исправлений или форматирования применение недоступно.
- На анализ отведено до 120 секунд, на форматирование — до 30 секунд. Задачу можно отменить.
- Пользователь должен просмотреть предложенный результат перед применением.
